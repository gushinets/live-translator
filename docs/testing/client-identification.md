# Идентификация клиента и шаблона переводчика

Каждая новая попытка в существующем usage ledger может содержать два диагностических поля:

- `client_build_id` — имя реально загруженного JS-бандла, например `bundle:index-HASH.js`; в dev — `development`. Клиент с этой поддержкой, загруженный из PWA-кеша, передаст идентификатор своей сборки, даже если сервер уже обновился.
- `interpreter_prompt_id` — `sha256:` нормализованного исходного модуля `LivePrompts.ts`, автоматически вычисленный Vite при сборке. Это версия шаблонов, включая стартовые инструкции, а не хеш конкретного текста с выбранными языками и контекстом разговора. Изменение комментариев в модуле тоже меняет идентификатор.

Клиент сообщает сборку уже при запросе создания provider-сессии. Идентификатор шаблона попадает в существующие usage-отчёты после подтверждения стартовых инструкций переводчика (`first_steering`, после interpreter contract). Поэтому при сбое до этого подтверждения поле остаётся `NULL`. Это диагностические сведения от клиента, а не независимая проверка провайдером фактически применённого текста.

Доставка использует заголовки `X-Live-Translator-Build` и `X-Live-Translator-Prompt`. Строгий JSON-контракт запросов не меняется; предыдущий API игнорирует новые заголовки. В очереди IndexedDB идентификаторы лежат в `usage.clientMetadata`, рядом с прежним `usage.report`: уже открытая старая вкладка может доставить отчёт без новых заголовков и без HTTP 400. Новый worker восстанавливает заголовки из соседнего поля, сохраняя исходную сборку после обновления страницы. Сервер сохраняет первое непустое значение каждого поля; некорректные заголовки игнорируются без отказа в учёте usage.

После first-steering ACK `LiveClient` сразу передаёт ID шаблона в учёт, до ожидания открытия микрофона или завершения восстановления. Если провайдер закрывается во время этих ожиданий, финальный отчёт уже содержит подтверждённый ID.

## Просмотр

В авторизованном владельцем ответе `GET /api/live/session/:id` поля называются `clientBuildId` и `interpreterPromptId`. На сервере доступны те же значения:

```sql
SELECT id, state, client_build_id, interpreter_prompt_id
FROM live_sessions
ORDER BY creation_requested_at DESC
LIMIT 20;
```

Старые строки и клиенты без этой возможности остаются с `NULL`: исторические значения не восстанавливаются предположениями. `app_version` и `prompt_version` сохраняют прежний смысл версии протокола клиента и начального серверного промпта.

## Миграция и откат

Миграция `004-client-identification.sql` добавляет две nullable-колонки. `user_version` остаётся 2, как при предыдущем расширении usage identity: предыдущий API может работать с базой, игнорируя новые поля. База автоматически назад не перематывается.

После миграции для backup/verify/restore нужно использовать обновлённые CLI-инструменты, в том числе при откате API-образа: старый строгий проверяющий код не принимает дополнительные колонки. Новые инструменты проверяют и старую, и расширенную схемы; backup/restore сохраняет идентификаторы.

Текст, аудио, SDP и секреты не добавляются в отчёты. Это расширение существующих метаданных, без отдельного журнала событий или нового сервиса.

Локально 2026-10-30: 2209 unit/integration-тестов, production-сборки API и web, проверки типов и ESLint изменённых файлов прошли. Добавлены регрессии закрытия между ACK и открытием микрофона, старого JSON-формата очереди и восстановления идентификаторов другим worker. Потребитель из базового коммита `c27f031b` проверен отдельно: с прежним форматом PR получал HTTP 400, с исправленным — HTTP 200 и подтверждал доставку. Четыре браузерные проверки в Chromium/WebKit подтвердили имя реально загруженного бандла и доставку идентификатора промпта через IndexedDB после сбоя HTTP. Провайдер в браузерных проверках имитировался; платных запросов и изменений на продакшне не было.
